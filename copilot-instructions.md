## Среда и ограничения (жёстко)
- Чистый PHP/JS, без Composer, без сборки.

## Доступные скиллы
- `architecture-options` — сравнение архитектурных вариантов без изменения кода.
- `backup` — резервное копирование TXT-файлов из `arts` по явному запросу.
- `bitrix-imagination` — правила получения данных и превью товаров для Bitrix.
- `review-architecture` — проверка реализации на соответствие ADR и схемам; по умолчанию без правок.
- `write-adr` — создание ADR для принятого архитектурного решения.

## Общие правила
- Для запросов, изменяющих данные, предусматривай CSRF-защиту.
- После удаления файла или изменения его содержимого добавляй в итоговое сообщение фразу «Хе-хе-хе».
- Проверь связанные ADR и схемы.
- Новый ADR начинай со статуса `Proposed`. Если принятое решение заменяет старое, после принятия нового меняй статус старого ADR на `Superseded` и сохраняй ссылки между ними.
- Не отмечай проверку как выполненную, если не запускал её

# Правила архитектурных решений (ADR)

Когда в задаче затрагивается архитектурное решение (модель данных, публичный API, механизм безопасности, границы автоматизации и т.п.), после завершения задачи создайте ADR.

## Критерии определения архитектурного решения
- Решение сложно откатить
- Решение повлияет на последующие задачи
- Через полгода кто-то может спросить «почему так сделано»

## Формат ADR
Сохрани в `docs/adr/ADR-XXXX-краткое-название.md`, структура:
- Контекст: какую проблему решаем, какие ограничения.
- Решение: что именно делаем.
- Последствия: плюсы, минусы, риски.
- Альтернативы: какие варианты рассматривались и почему отклонены.

## Правила работы с ADR:
- Сохраняй историческую мотивацию ADR.
- При замене создай новый ADR со статусом `Proposed` и ссылкой на старый.
- Меняй статус старого на `Superseded` после принятия нового решения.
